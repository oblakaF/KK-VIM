## 2. ИЕ-1 — предпосылка П-3

### 2.1. Вывод QA, проверенный независимо

**Лемма о кратности** (вывод QA; я сверил его по шагам).
- Нормальное binary64 x с двоичным порядком e(x) (|x| ∈ [2^{e}, 2^{e+1})) имеет вид m·2^{e−52}, где m — целое, 2⁵² ≤ |m| < 2⁵³.
- Значит, xy кратно 2^{e(x)+e(y)−104}.
- При e(x) + e(y) ≥ −918 показатель e(x) + e(y) − 104 ≥ −1022, и xy кратно G := 2⁻¹⁰²².

**Сохранение кратности при округлении.** Пусть t = kG, k — целое. Тогда:
- при |k| < 2⁵³ число t представимо точно (53 значащих бита, порядок ≥ −1022), и округление его не меняет;
- при |k| ≥ 2⁵³ имеем |t| ≥ 2⁻⁹⁶⁹. Округление монотонно, поэтому |fl(t)| ≥ 2⁻⁹⁶⁹, ulp(fl(t)) ≥ 2⁻¹⁰²¹, и fl(t) кратно G.

Формулировка QA «результат точен либо его ulp ≥ G» верна.

**Проверка округления.** Корректное округление `float(Fraction)` для 5 000 случайных k < 2⁶², 45 значений k около 2⁵³ и трёх больших k: ни одного результата, некратного G, и ни одного субнормального. Произведения с e(x) + e(y) = −918 кратны G, с −919 — нет.

**Достаточность для порядков суммирования и FMA.** В dgemm при длине N ≤ 3 участвуют:
- произведения входов;
- сложения;
- FMA вида fl(ab + c), где c — предыдущий частичный результат;
- умножение на α = 1 (точно); C при β = 0 не читается (П-4).

По индукции каждый промежуточный результат — округление суммы кратных G, то есть кратное G. Ненулевое кратное G по модулю ≥ G = 2⁻¹⁰²², поэтому оно не субнормально. Вывод не зависит от порядка суммирования и от наличия FMA.

**Следствие, которое QA не отметил.** При `P3_CONFIRMED` режимы FTZ и DAZ не влияют на результат: субнормальных входов нет (они отсеиваются раньше), субнормальных результатов быть не может. Подтверждение П-3 поэтому не опирается на самопроверку FTZ/DAZ (Н-1).

**Критерий в коде.**
- Минимумы порядков ненулевых элементов берутся по столбцу k отдельно для X и для Y. В поле участвуют все пары (i, j), поэтому минимум суммы порядков реализуется некоторым произведением: критерий точен, а не только достаточен.
- `frexp` даёт m ∈ [½, 1), отсюда e = ex − 1. Верно.

### 2.2. Граничные случаи (мой прогон; BLAS этой машины использует FMA)

Конструкция: два произведения с e(x) + e(y) = e_Σ так, что их точная сумма равна наименьшему возможному ненулевому значению.

| e_Σ | точная сумма | порядок столбцов | ŵ | статус | ВОК-4/5 |
|---|---|---|---|---|---|
| −918 | G = 2⁻¹⁰²² | прямой | 0 | `P3_CONFIRMED` | HOLDS / HOLDS |
| −918 | G | обратный | G (нормальное) | `P3_CONFIRMED` | HOLDS / HOLDS |
| −919 | G/2 | прямой | 0 | `UNRESOLVED_PREMISES` | статус предпосылки |
| −919 | G/2 | обратный | **G/2 — субнормальное** | `OUTSIDE_P3` | статус предпосылки |

- **Граница −918/−919 реальна.** При −919 субнормальный результат действительно возникает, если FMA выполняется в «неудачном» порядке. Значит, порог нельзя ослабить, и QA выбрал его правильно.
- **Порядок FMA влияет на ŵ** даже при −918: ŵ = 0 или G. Обе строки при этом HOLDS — погрешность в пределах γ₂S.

## 3. ИЕ-2 — предпосылка П-2 и диапазон double

**Конечность ŵ как свидетельство.** При округлении к ближайшему (П-1) переполнение даёт ±∞.
- Дальше в dgemm следуют только сложения и FMA с произведениями конечных входов. Поэтому ±∞ сохраняется или превращается в NaN (∞ − ∞).
- Умножения промежуточного результата на 0 в этой модели нет.
- Значит, конечное ŵ доказывает отсутствие переполнения при образовании.
- Условие — П-1. При направленном округлении к нулю переполнение дало бы ±DBL_MAX, и вывод бы не действовал (Н-б).

**Прогон с предупреждениями, превращёнными в ошибки:**

| Случай | статус | результат |
|---|---|---|
| (а) X = Y = 10²⁰⁰ | `OUTSIDE_P2` | 4 неконечных узла; max\|w̃\| вверх = inf; e, ВОК-4/5, (iv) не вычисляются |
| (б) (10³⁰⁸, 10³⁰⁸, −10³⁰⁸) × 𝟏, точная сумма 10³⁰⁸ | `OUTSIDE_P2` | max\|w̃\| вверх = 10³⁰⁸ |
| (в) поле ~10³⁰⁰, (iv) в double переполняется | `P3_CONFIRMED`, HOLDS | ‖ŵ‖_a = [1,6971·10³⁰¹, 1,6971·10³⁰¹]; (iv) = `'inf'`, ошибка UNRESOLVED |
| (г) поле ~10³⁰⁶ на 100 × 100, ‖ŵ‖_a > DBL_MAX | `P3_CONFIRMED`, HOLDS | интервал **[DBL_MAX, +∞]**; (iv) — `'inf'` и `'nan'`, ошибка UNRESOLVED |
| (д) −10²⁰⁰ · 10²⁰⁰ → −∞ | `OUTSIDE_P2` | — |
| (е) ∞ − ∞ → NaN | `OUTSIDE_P2` | max\|w̃\| = 0 (точное поле нулевое) |
| точная сумма DBL_MAX + ½ulp (ничья к чётному даёт ∞ — переполнение по IEEE) | `OUTSIDE_P2` | верно |

- **Нижняя граница выше DBL_MAX** равна DBL_MAX (`_down`) — это верная нижняя граница; верхняя — +∞ (`_float_up`). Модуль Q1b не менялся.

## 4. ИЕ-3 — область входов

**Закрыто** (мой прогон):

| Вход | Поведение |
|---|---|
| lₓ, l_y, D: 0, −1, −0,0, ±∞, NaN, `True`, строка, `1 + 0j`, `Fraction(1, 3)`, 0-мерный массив | `ValueError` до вычислений |
| целое lₓ = 2⁵³ + 1; `np.uint64(2⁶⁴ − 1)`; 2¹¹⁰⁰ | `ValueError`: не представимо точно / вне диапазона |
| `np.int64(2⁵³)`, `np.float32(0,1)`, `np.float16(0,1)` | принимаются **точно**: двоичные числа меньшей точности расширяются без потерь |
| nₓ = 2, 4,0, `True`, `np.float64(4)` | `ValueError` |
| nₓ = `np.uint8(4)` | принимается, приводится к `int` |
| X: complex (в том числе с нулевой мнимой частью), bool, str, object (включая Python-целые > 2⁶⁴), datetime64, timedelta64 | `ValueError` |
| X int64 = 2⁵³ + 1, 2⁶³ − 1; uint64 = 2⁶⁴ − 1 | `ValueError` (обратное приведение не совпадает; переполнение обратного приведения ложного равенства не даёт) |
| X int64 = −2⁶³ (точно представимо); float32; −0,0 | принимаются точно |
| X longdouble | проверка обратным приведением `astype(arr.dtype) == arr` отклоняет неточное значение |

**ИЕ-3а — не закрыто.** `_positive_real` (стр. 76–88) проверяет точную представимость только для целых: `isinstance(v, (int, np.integer))`. Для `np.floating` выполняется только `f = float(v)`.
- `numpy.longdouble` — подкласс `np.floating`. На x86-64 Linux и macOS Intel это 80-битный формат (`np.finfo(np.longdouble).nmant = 63`), на Linux aarch64 — двоичный128 (112).
- `float(v)` округляет к ближайшему double без сообщения.
- **Контрпример** (на этих платформах): lₓ = `np.longdouble(1) + np.longdouble(2)**-60` принимается как lₓ = 1,0. SHA-256 и измерение относятся к 1,0, и никакой пометки нет.
- Это противоречит docstring модуля («exactly representable») и address-fix («точно представимые в double»).
- Массив того же типа, наоборот, отклоняется. Обработка непоследовательна.
- **На этой машине** (Windows, `nmant = 52`; long double совпадает с binary64) случай не воспроизводится. Поэтому существующие тесты его не видят.

**Требуется:**
- в `_positive_real` для `np.floating` (или для любого не-`float`) сравнивать `Fraction(f)` с точным значением аргумента, например `Fraction(*v.as_integer_ratio())`, и при неравенстве давать `ValueError`; либо явно ограничить область типами `float`, `np.float16/32/64`;
- тест: на платформах с широким long double — прямой, иначе пропуск с причиной; либо проверка на заглушке с методом `as_integer_ratio`.
