## 2. ИЕ-3а

**Код** (`_positive_real`):
1. Сначала вычисляется f = `float(v)`, проверяются диапазон, конечность и знак.
2. Затем вычисляется **точное** значение аргумента:
   - `Fraction(int(v))` для `int` и `numpy.integer`;
   - `Fraction(*v.as_integer_ratio())` для `float` и `numpy.floating`, включая `numpy.longdouble`.
3. Если `Fraction.from_float(f)` с ним не совпадает — `ValueError`.
4. Если точное значение определить нельзя — тоже `ValueError`, без допуска.

Сравнивается результат `float(v)` с независимо полученным точным значением. Поэтому проверка закрывает и молчаливое округление, и подтипы с несогласованными `__float__` / `as_integer_ratio`.

**Мой прогон** (Windows, `np.finfo(np.longdouble).nmant = 52`):

| Вход lₓ | Результат |
|---|---|
| подкласс `float`: double 1,0, точное значение 1 + 2⁻⁶⁰ (как расширенный long double) | `ValueError`: не представимо точно |
| подкласс `float` с точным значением 2⁻¹¹⁰⁰ при double 5·10⁻³²⁴ | `ValueError` |
| подкласс `float` с ложным `__float__` (2,0 при значении 1,0); подкласс `int` с ложным `__float__` | `ValueError` |
| подкласс `float` без определимого точного значения | `ValueError`: «cannot be determined» |
| `np.longdouble(0,1)` (здесь binary64), `np.float16(0,1)`, `np.float32(0,1)` | принимаются, значение сохраняется точно |
| 2¹⁰²³ | принимается точно |
| 2¹⁰²⁴; 2⁵³ + 1; `np.uint64(2⁶⁴ − 1)` | `ValueError` |
| 5·10⁻³²⁴ | принимается: значение положительно и точно |
| −0,0; `np.int8(−3)`; `np.bool_(True)` | `ValueError` |

**Расширенный long double.** На этой платформе его нет, поэтому 4 теста QA с ним пропускаются, причина указана (`-rs`).
- Логику на любой платформе проверяет `test_ie3a_logic_on_every_platform` на подклассах `float`. Тот же приём я применил выше.
- CI проверен владельцем: прогон `39942107985`, все пять задач — SUCCESS. На Ubuntu (Python 3.13 и 3.14) все 4 теста расширенного long double имеют статус PASSED; на Windows они пропущены по платформенной причине. Матрица `.github/workflows/ci.yml` действительно включает `ubuntu-latest` и `windows-latest`.
- Журналы CI я сам не просматривал: GitHub CLI на этой машине не установлен. Выполнение тестов на Linux подтверждено владельцем по прогону `39942107985`, а не мной.

**Замечание редакционное, не блокирующее.** Расширенный long double вне диапазона double (2¹¹⁰⁰ или 2⁻¹¹⁰⁰) отклоняется ещё на шаге 1:
- после `float(v)` получается ±inf или 0;
- для 2⁻¹¹⁰⁰ сообщение гласит «must be finite and > 0», хотя значение положительно.

Отказ при этом верный, ложного допуска нет.

## 3. Н-а, Н-б, Н-в

- **Н-а.** Docstring теперь делит причины `OUTSIDE_P3` на две группы:
  - случаи, где субнормальная операция точно произошла: субнормальный ŵᵢⱼ; единственное ненулевое произведение ниже 2⁻¹⁰²²;
  - субнормальный вход — консервативное ограничение области, «even when no subnormal operation actually occurs». Пример — субнормальный элемент против нулей второго множителя.

  Это совпадает с моим разбором в `f5f85e1`, разд. 2.3.
- **Н-б.** Docstring П-2 прямо опирается на П-1: при округлении к ближайшему переполнение даёт ±∞, а при округлении к нулю дало бы ±DBL_MAX, и вывод бы не действовал.
- **Н-в.** `_real_array` отклоняет `numpy.ma.MaskedArray` и его подклассы (`isinstance`) — и для X, и для Y, даже без замаскированных элементов (тест и мой прогон).
  - `np.matrix` по-прежнему принимается. Это допустимо: `np.asarray` не теряет его данные.
