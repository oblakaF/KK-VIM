Цели: G2, G3.3, G4. Роль: QA. База плана: `main` @ `8c4dbe1f7ac5d9a8bd71d227139459a90544089a`.

План фиксирует до получения результатов нового Builder:
- выборки;
- априорные допуски;

невозможно выполнить так, как описано, это записывается в отчёт как отклонение с причиной; критерий при этом не заменяется.

## 0. Общие правила

1. **Статусы проверки:**

   | Статус | Значение |
   |---|---|
   | PASS | критерий выполнен на всей заявленной выборке |
   | FAIL | критерий нарушен хотя бы в одном случае. Сообщается воспроизводимый случай; исправление кода Builder QA не выполняет |
   | UNRESOLVED | решение невозможно по заранее указанной причине: величина в пограничной полосе, предпосылка модели не выполнена, проверка невыполнима без изменения публичного API. UNRESOLVED не PASS и не FAIL |

2. **Допуски — только априорные:**
   - модели округления спецификаций и QA (указаны в каждом пункте);
   - принятые числа D-048;
   - правило 1/100 D-046.

   Наблюдённые значения сообщаются как запас и **не** становятся допусками. Коэффициенты моделей (например, 7u) по наблюдениям не меняются.
3. **Побитовое равенство** требуется только при фиксированном порядке операций: одна платформа, одно окружение, один и тот же путь вычисления
   (AGENTS.md, разд. 4). Между платформами (Ubuntu, Windows) сравнение ведётся по моделям округления, указанным ниже.
4. **Область.** Квалифицированная область — только та, что указана в D-048 для каждого пункта:
   - n = 320 семейства I — **новая независимая проверка QA вне утверждённой области**; её результат область D-048 автоматически не расширяет;
   - n = 1280 для остановки — **исследовательская** проверка; полного подтверждения нет.
5. **Научные статусы.** QA проверяет, что их сохраняет реализация (К-8), и сам их не меняет:
   - результаты исследовательского режима — PROVISIONAL / NOT_QUALIFIED;
   - статусы группы B (`status_cont_*` = PROVISIONAL при s ≥ 2) не переклассифицируются;
   - Q-022, Q-020, Q-025 — OPEN.
6. **Конечная дискретная задача и неусечённый непрерывный метод не смешиваются.** Точность реализации не смешивается с точностью КК-МВИ (D-025).
7. **Высокая точность** (`mpmath`, ≥ 50 знаков) — только во временном окружении QA, вне обязательного CI. В CI — только проверки без `mpmath`;
   там, где нужен высокоточный эталон, используется `decimal` стандартной библиотеки.
8. Код Builder, принятые спецификации и DECISIONS QA не меняет. Тестовая инъекция ошибок — только через `monkeypatch` внутренних функций в
   тестах, без изменения публичного API.

## К-2. Остановка (D-048.3, D-048.4)

**Выборка:**

| Группа | N | r | Сетки | Статус группы |
|---|---|---|---|---|
| Область D-048.3 | 2, 3 | 1/5, 1, 5 | семейство I n = 40, 160, 640 | квалификация в области |
| Независимая проверка | 2, 3 | 1/5, 1, 5 | n = 320 | вне утверждённой области |
| Исследовательская | 2, 3 | 1/5, 1, 5 | n = 1280 | только наблюдение |

`research_mode=True`, `transform="fft"`, число полушагов — по умолчанию новой реализации.

**Независимая проверка критерия.**
- QA вычисляет по сохранённым полям каждого полушага собственные ε_s^∞ и ε_s^E — тем же определением (NUMERICAL_SPEC 11.1; R4_NUMERICAL_SPEC 7),
  но своей реализацией без функций Builder:
  - ε^∞ = max|w_s − w_{s−1}|/max|w_s|;
  - ε^E — энергетическая норма разности по двумерной сборке Δ_h (`kkvim_reference.r4_spectral_control.nodal_laplacian`) против ‖w_s‖_{a_h}.
- Ожидаемый полушаг остановки s_QA — первый s ≥ s_min = 3, для которого ε^∞ ≤ 10⁻¹⁰ и ε^E ≤ 10⁻⁸ одновременно на s − 1 и s.
- **Пограничная полоса** (априорно): решение UNRESOLVED, если на каком-либо полушаге s ≤ s_QA, где сравнение с допуском определяет исход,
  значение QA лежит в полосе |ε^E − tol_E| ≤ ε_floor^(N) или |ε^∞ − tol_∞| ≤ 100u. Обоснование: две реализации одной величины расходятся не больше
  чем на её пол округления.

**Критерии:**
1. Статус PROVISIONAL_FIELD_STABILIZED при s_stop = s_QA < s_max = 100 во всех расчётах области.
   - PASS — все совпадают;
   - FAIL — любое расхождение s_stop ≠ s_QA вне пограничной полосы или отсутствие статуса;
   - UNRESOLVED — пограничная полоса.
2. **Численный пол.** ε_floor^(N) реализации совпадает с независимо вычисленной формулой D-048.3 10u(max(n_x, n_y)/π)²·√N/(1 − γ_N√N),
   γ_N = Nu/(1 − Nu), с относительным допуском 4u (несколько округлений одной формулы).
3. **ERROR_INPUT.** Конфигурации с tol_E < 10·ε_floor^(N) отвергаются статусом ERROR_INPUT **до** первого полушага. Проверяются две
   конфигурации по обе стороны границы:
   - если tol_E — параметр API, — tol_E = 10·ε_floor^(N)·(1 ± 10⁻³);
   - иначе — наименьшие чётные n по обе стороны границы n* = π·(tol_E/(100u·√N/(1 − γ_N√N)))^{1/2}; для N = 3 и tol_E = 10⁻⁸ n* ≈ 2265.

   Если граница непроверяема без изменения API — UNRESOLVED.
4. **s_min.** Статус стабилизации не присваивается при s < 3. Проверка: журналы выборки; тестовая инъекция `monkeypatch`, при которой критерий
   выполнен уже на s = 2, — ожидается остановка ровно на s = 3.
5. **s_max.** При недостижении стабилизации к s_max — MAX_HALF_STEPS. Проверка — тестовой подменой s_max (например, 5) через `monkeypatch`
   внутренней константы. Если константа недоступна без изменения API — UNRESOLVED.
6. **Защиты до статуса.** PROVISIONAL_FIELD_STABILIZED присвоен только при пройденных защитах ранга D-048.5 на **всех** полушагах до s_stop
   (журнал).
7. **`research_mode=False`.**
   - После s = 1 — NOT_QUALIFIED, без QR и без вычисления исследовательского критерия стабилизации (в журнале нет статуса стабилизации и QR).
   - Прежняя специальная семантика `half_steps=1` (HALF_STEP_LIMIT_REACHED, без QR) сохраняется.

   Любое изменение этого поведения — FAIL (D-048.3, «Область действия»).
8. **n = 320** — критерии 1, 2, 6 проверяются как независимая проверка вне области. Результат сообщается отдельно, область не расширяет.
9. **n = 1280** — только наблюдение: s_stop, запас tol_E/(10ε_floor^(N)), плато ε^E. Ни PASS, ни FAIL области не выдаётся.

## К-4. Невязка (D-048.2)

1. **Порог.** η_N ≤ 10⁻¹² на всех полушагах расчётов К-2 и К-3 (область D-048.2: семейство I n ≤ 1280 и шесть сеток семейства II). Сообщается
   запас 10⁻¹²/max η_N. Нарушение без последующего успешного уточнения — FAIL.
2. **Независимая проверка невязки.** η_N реализации сравнивается с η_QA:
   - η_QA вычисляется по сохранённым A, B, C, F и решённому набору;
   - применение оператора 𝒦 — собственной реализацией QA (`qa_apply_K` из `test_r4_controller_comparison.py`, вторые разности без DST);
   - нормировка — по R4_NUMERICAL_SPEC 3.3.

   Допуск: |η − η_QA| ≤ 16u (существующая проверка того же теста). Функция невязки Builder для получения η_QA не используется.
3. **Инъекции ошибок** — `monkeypatch` внутреннего модального решателя в тесте, без публичных параметров:
   - (а) **исправимое возмущение.** Выход модального решения при первом вызове на полушаге искажается относительным возмущением 10⁻⁸ (η ≫ 10⁻¹²).
     Ожидается ровно один шаг уточнения, итоговое η_QA ≤ 10⁻¹², расчёт продолжается. PASS — все три условия;
   - (б) **неисправимое возмущение.** Выход искажается на каждом вызове так, что после одного уточнения η_QA > 10⁻¹²: постоянное аддитивное
     смещение 10⁻⁶·max|v|. Ожидается ERROR_LINEAR_SOLVE после одного шага уточнения, без второго. PASS — статус и число уточнений = 1;
   - (в) **нет лишнего уточнения.** Без инъекции модальный решатель на полушаге вызывается ровно один раз (счётчик через `monkeypatch`-обёртку),
     если η ≤ 10⁻¹². Лишний вызов — FAIL.

   Если внутренний решатель недоступен для подмены без изменения публичного API — UNRESOLVED.

## К-6. Плотное DST (D-048.6, аудит разд. 3)

**К-6.0. Предпосылка точности `np.sin` (исследуется независимо, до проверки модели 7u).**

- **Аргументы.** Фактические double-аргументы x, которые реализация `dense` передаёт в `np.sin`. Они восстанавливаются **тем же выражением**,
  что в коде Builder (после исправления). Восстановление проверяется побитовым совпадением √(2/n)·np.sin(x) со знаком с элементами Ψ Builder
  на той же платформе. Без совпадения — UNRESOLVED (аргументы не установлены).
- **Измерение (раздельно):**
  1. ошибка `np.sin(x)` относительно высокоточного sin **того же double x**, в ulp результата: |np.sin(x) − sin(x)|/ulp(np.sin(x));
  2. ошибка формирования x относительно математического πm/n: |x − πm/n| — абсолютная и в ulp(x);
  3. путь вызова: одномерный массив аргументов и двумерный массив той же формы, что в `sine_matrix`. Сравнивается также побитовое
     равенство результатов 1D и 2D — у них могут быть разные SIMD-пути.
- **Фиксируется:** максимальная ошибка в ulp (по 1D и 2D отдельно), число аргументов, версии NumPy и Python, ОС, процессор и доступный SIMD-путь
  NumPy (`numpy._core._multiarray_umath.__cpu_features__` или `np.show_runtime()` — что доступно).
- **Платформы:**
  - локальная машина QA — эталон `mpmath`, 50 знаков;
  - CI Ubuntu и Windows — эталон `decimal`, 50 знаков, без `mpmath`.

  Тест CI выводит максимальную ошибку в ulp и сведения о платформе в журнал pytest. Утверждение проверяется отдельно на каждой платформе.
- **Правило интерпретации:**
  - предпосылка «≤ 1 ulp» **подтверждена** на платформе ⇒ на этой платформе проверяется условная модель QA 7u (К-6.2) в её установленной
    области — аргумент после полного приведения к [0, π/2];
  - предпосылка **нарушена** (> 1 ulp хотя бы на одном аргументе) ⇒ она отмечается как НЕ ВЫПОЛНЕННАЯ на этой платформе, а квалификация модели 7u
    — UNRESOLVED / NOT_QUALIFIED на ней;
  - корректность алгоритма приведения (К-6.1) оценивается отдельно и от этого не зависит;
  - коэффициент 7u не заменяется на 4 ulp или иное наблюдённое число без нового априорного вывода и согласования;
  - заранее не утверждается, что предпосылка верна на всех процессорах.

**К-6.1. Приведение аргумента и знак (точные проверки, одна платформа, побитово).**

Ψ_ik = √(2/n)·sin(πik/n), i, k = 1…n − 1. Реализация обязана выполнять приведение по D-048.6:
- m = ik mod 2n;
- при m ≥ n — m − n и знак −1;
- при 2m > n — n − m.

Проверяется:
1. **Точные нули.** Ψ_ik == 0.0 при ik ≡ 0 (mod n).
2. **Симметрия.** Ψ == Ψᵀ побитово.
3. **Знаковая антисимметрия** (следствие приведения): Ψ_{i,n−k} == (−1)^{i+1}·Ψ_{i,k} побитово при всех i, k. Оба элемента приводятся к одному и
   тому же r и отличаются только знаком.
4. **Совпадение со своим алгоритмом приведения.** Независимая реализация QA того же целочисленного приведения (собственный код) даёт тот же
   массив аргументов. Сравнение аргументов побитовое, элементов — по К-6.2. Эталонные значения синуса QA не берёт из функций Builder.
5. При n = 40, 160, 640, 1280 — PASS, если все четыре проверки выполнены; FAIL — любое нарушение.
